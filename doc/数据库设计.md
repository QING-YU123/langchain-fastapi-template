### 💡 下一步动作确认

有了这套清晰的数据字典，你的前后端数据边界就完全确定了。

**我们接下来的重点可以放在以下两个硬核逻辑中选一个：**

1. **Hono API 路由设计：** 如何规划 RESTful 接口（例如 `POST /api/capture`），让 Electron 能够丝滑地把数据喂给 PG？
    
2. **SRS 调度算法逻辑：** 当你在对弈记录表（`evaluation_debates`）中拿到一个 `C`（代表回答得很差）时，数据库如何计算出明天必须让你再看一遍的具体数学公式？

理解这些表之间的关联，是接下来在 NestJS 中配置 TypeORM 实体（Entities）和联表查询的基础。

整个数据库的架构采用的是经典的**“星型拓扑 (Star Topology)”**：`articles`（网页快照主表）是绝对的核心枢纽，其他四张表作为扩展属性或历史记录，紧密围绕并依赖于它。

以下是具体的表间关系与业务逻辑说明：

### 核心 ER 关系映射表

|**主表 (中心)**|**关系类型**|**从表 (分支)**|**外键约束与操作**|**业务场景映射**|
|---|---|---|---|---|
|`articles`|**1 : 1**<br><br>  <br><br>_(一对一)_|`ai_distillations`<br><br>  <br><br>_(教案表)_|`UNIQUE`<br><br>  <br><br>`ON DELETE CASCADE`|**脱水绑定：** 一篇文章只配有一份专属的 AI 导读教案。如果文章被彻底删除，教案也会随之物理销毁。|
|`articles`|**1 : 1**<br><br>  <br><br>_(一对一)_|`review_schedules`<br><br>  <br><br>_(调度表)_|`UNIQUE`<br><br>  <br><br>`ON DELETE CASCADE`|**时钟绑定：** 一篇文章在系统中只有一个“生命周期时钟”。解耦出来是为了不让高频更新的复习倒计时干扰主表的读取性能。|
|`articles`|**1 : N**<br><br>  <br><br>_(一对多)_|`article_embeddings`<br><br>  <br><br>_(向量表)_|`ON DELETE CASCADE`|**切块存储：** 一篇万字长文会被大模型切分为多个 Chunk（比如 5 段），每段生成一个向量。查询时匹配到具体的段落，再反查出所属的 `article_id`。|
|`articles`|**1 : N**<br><br>  <br><br>_(一对多)_|`evaluation_debates`<br><br>  <br><br>_(对弈表)_|`ON DELETE CASCADE`|**历史追溯：** 随着时间推移，AI 导师会针对同一篇文章对你进行多次“抽查”。每一次完整的“提问-回答-评分”都会作为一条独立记录追加下来，形成你的学习成长轨迹。|

### 💡 架构设计上的三个关键巧思

为了让这套系统在 Electron + PostgreSQL 环境下跑得足够健壮，关系设计中隐藏了以下几个考量：

1. **极致的级联销毁 (`ON DELETE CASCADE`)**
    
    由于这是一个个人知识管理工具，用户的“清理”动作必须干净利落。只要你在主界面将某篇 `article` 移入垃圾篓并清空，数据库会自动沿着这些外键关系，瞬间抹除它的向量数据、AI 教案、复习计划和所有的对弈历史，绝不留下数据孤岛和存储碎片。
    
2. **读写分离的雏形（主表与调度表的 1:1 解耦）**
    
    你可能会问：_“既然是 1:1，为什么不把下次复习时间 (`next_review_at`) 直接塞进 `articles` 表里？”_
    
    因为 `articles` 存的是极长的大文本（Markdown），而调度引擎（Cron Job）每隔几分钟就要疯狂扫描和更新复习时间。将它们拆开，可以保证后端 NestJS 在高频轮询调度状态时，不需要把沉重的文章正文加载到内存里。
    
3. **不可变记录的追加 (Append-Only)**
    
    `evaluation_debates` (对弈表) 是一种不可变记录。我们永远不修改过去的对弈历史，只做 `INSERT`。这样你未来可以清晰地画出一条折线图：_“我对这篇关于 DFA alpha 1 算法的文章，从最初的 C 级理解，是如何在 4 次反刍后提升到 A+ 级的。”_

## Gemini 说

为了让状态机（State Machine）的流转在代码层面绝对清晰，并且高度契合我们“认知代谢”的哲学，我为你将这 5 个状态定义为标准的英文枚举（Enum），并明确了它们的边界和触发条件：

### 核心代谢状态枚举 (Metabolic Status Enums)

|英文枚举 (Enum)|中文映射|状态定义与业务边界 (Definition & Boundary)|状态流转条件 (Transitions)|
|---|---|---|---|
|**`INBOX`**|收件箱|**初始捕获态：** 刚刚通过快捷键抓取，AI 尚未完成“脱水”或你还未对其进行初始的“要不要读”的判定。它是未经处理的信息原石。|捕获成功 → `INBOX`|
|**`COOLING`**|冷却中|**强制镇静态：** 触发了防积压机制。文章已被锁定，在设定的冷却倒计时（如 2 小时）结束前，系统拒绝为你展示正文内容。用于对抗“冲动型收藏”。|从 `INBOX` 移入待看 → `COOLING`|
|**`READY`**|待阅|**待吸收态：** 冷却完毕，且 AI 已备好“导读教案”。它正躺在你的“今日必读”或“闲暇队列”中，等待你进行第一次深度的“初级代谢”（正式阅读）。|冷却时间到 → `READY`|
|**`REVIEWING`**|复习中|**循环反刍态：** 核心代谢区间。你已经完成了首读，文章正式被 SRS（间隔复现）调度引擎接管。系统会根据你的记忆衰减曲线，定期向你发起“导师提问”。|首读完成 → `REVIEWING`|
|**`INTERNALIZED`**|已入骨|**终极同化态：** 知识已化为直觉。在多次复习对弈中，你连续获得了高分（如连续 3 次 A），系统判定该知识点已被你彻底吸收，不再主动推送，仅在“语义织网”碰撞时作为背景知识被唤醒。|掌握度达到阈值 → `INTERNALIZED`|

### 💡 给你的代码落地建议

既然你使用 **PostgreSQL + Drizzle/TypeORM**，强烈建议在数据库层面直接使用 **PostgreSQL 原生的 `ENUM` 类型**，而不是普通的 `VARCHAR`。

这样能在数据库底层就锁死这 5 个状态，防止后端代码手滑写成 `review` 或 `Reviewing` 导致的脏数据。

在 Drizzle 中，你可以这样优雅地定义：

TypeScript

```
import { pgEnum } from 'drizzle-orm/pg-core';

export const metabolicStatusEnum = pgEnum('metabolic_status', [
  'INBOX', 
  'COOLING', 
  'READY', 
  'REVIEWING', 
  'INTERNALIZED'
]);
```

现在的整个状态流水线非常严密，就像一个精密运转的齿轮。
